The existing repository describes IdeaCFG as an “Idea to CFG Converter” and already implements a modular pipeline from input and IR construction through CFG/DCG generation, optimisation, validation, explanation, and export.   The requirements below preserve that architecture while adding typed, non-chatbot-recordable evidence sources and department-specific interpretation.

CFG Converter 2

GitHub Copilot Agent Prolog Program Requirements

Proposed repository: cfgconverter2
Source repository to copy: https://github.com/luciangreen/cfgconverter
Implementation language: SWI-Prolog
Primary deliverable: PROGRAM_REQUIREMENTS.md

⸻

1. Project Summary

CFG Converter 2 shall be created as a working copy and extension of CFG Converter.

The original system converts human ideas, sentences, structured terms, concepts, relationships, and mathematical operations into:

* Context-free grammar rules;
* Executable Prolog DCGs;
* Supporting Prolog predicates;
* Validation reports;
* Explanations and traceability information;
* Exportable source files.

CFG Converter 2 shall extend this process so that grammar construction can also take account of non-chatbot-recordable data.

Non-chatbot-recordable data means observations, measurements, judgements, signals, indicators, records, or structured evidence that cannot be adequately represented as ordinary conversational text alone.

Examples include:

* Mathematical predicate formulae;
* Scientific measurements and instrument readings;
* Qualitative neuroolfactory unit measurements;
* Ranked sensory observations;
* Images, audio, sensor or laboratory metadata;
* Temporal and spatial observations;
* Humanities indicators;
* Intuitional assessments;
* Trust judgements;
* Confidence-weighted interpretations;
* Archival provenance;
* Expert annotations;
* Tacit or embodied observations represented through structured records.

The system shall convert both ordinary ideas and external evidence into CFG and DCG forms whose productions, constraints, semantic arguments, and outputs reflect the supplied evidence.

⸻

2. Central Design Principle

CFG Converter 2 shall distinguish between:

1. Grammar structure
    What sequences, alternatives, repetitions, classifications, and interpretations are permitted.
2. Computable operations
    Mathematical, logical, scientific, statistical, or deterministic operations that Prolog should compute directly.
3. Evidence conditions
    Measurements, observations, indicators, confidence values, provenance records, and expert judgements that constrain or support grammar rules.
4. Interpretive outputs
    Scientific classifications, mathematical results, humanities interpretations, intuitional conclusions, and explanations generated from the grammar and evidence.

The guiding rule shall remain:

Grammar represents structured possibilities; Prolog predicates compute operations; evidence predicates constrain or support interpretations.

No arbitrary external data shall be converted directly into executable Prolog source.

⸻

3. Required Repository Strategy

The GitHub Copilot Agent shall:

1. Copy the complete contents of luciangreen/cfgconverter.
2. Preserve the original licence, documentation history, tests, examples, and attribution.
3. Rename the extended program to CFG Converter 2.
4. Rename modules only where necessary.
5. Preserve backward compatibility with the original public API.
6. Add new modules rather than unnecessarily rewriting stable modules.
7. Keep the original CFG Converter behaviour available through compatibility predicates.
8. Document every intentional incompatibility.
9. Place the requirements in PROGRAM_REQUIREMENTS.md.
10. Maintain a staged progress log in PROGRESS.md.

The original repository shall remain unchanged.

⸻

4. Goals

CFG Converter 2 shall:

* Convert ideas and structured evidence into CFG and DCG representations.
* Support multiple academic departments through a common evidence model.
* Separate computations from grammar productions.
* Preserve the origin and provenance of every derived grammar rule.
* Permit qualitative as well as quantitative data.
* Represent uncertainty without pretending that uncertain evidence is certain.
* Represent intuition as structured indicators rather than unexplained truth.
* Generate executable and inspectable SWI-Prolog.
* Avoid dependence on a chatbot at runtime.
* Accept data produced outside conversational interfaces.
* Allow department-specific plugins without changing the core compiler.
* Explain why each generated rule exists.
* Validate generated grammars against evidence and test examples.
* Support parsing, generation, classification, and interpretation.
* Remain simple enough to operate through a Prolog API, CLI, and REPL.

⸻

5. Non-Goals

The first release shall not:

* Train neural networks;
* Perform unrestricted machine learning;
* Claim that intuition is objectively correct;
* Infer medical diagnoses automatically;
* Replace scientific instruments or expert review;
* Execute arbitrary code embedded in input data;
* Require cloud services;
* Require a chatbot;
* Attempt to understand every possible binary file format;
* Treat correlation as causation;
* Convert uncertain humanities judgements into false numerical precision;
* Guarantee that a generated grammar is a true scientific theory;
* Use unrestricted read/1, consult/1, call/1, or term_to_atom/2 on untrusted data.

10. Mathematics Requirements

Mathematics inputs may contain predicate formulae, equations, inequalities, domains, assumptions, definitions, and proof-step relationships.

Example input:

formula(f1, forall(X, implies(even(X), integer(X)))).
formula(f2, greater_than(X, 0)).
assumption(a1, member(X, integers)).

Required behaviour:

1. Mathematical expressions shall be extracted before ordinary grammar generation.
2. Formulae shall be converted to safe Prolog terms.
3. Declared operations shall become Prolog predicates or constraints.
4. Grammar rules shall describe valid expression or proof structures.
5. Mathematical computation shall not be simulated by terminal strings.
6. The generated DCG may carry expression trees as semantic arguments.
7. Variable scope shall be preserved.
8. Unsupported formulae shall remain quoted data with diagnostics.
9. CLP(FD) may be used for integer constraints.
10. CLP(R) may be optional for real-number constraints.
11. No formula text shall be passed to unrestricted call/1.

Example output:

proof_step(step(modus_ponens, A, B)) -->
    premise(A),
    premise(implies(A, B)),
    { valid_formula(A), valid_formula(B) }.

14. Intuitional Output Requirements

“Intuitional output” shall mean a conclusion selected by trusting one or more declared indicators.

It shall not mean unexplained guessing.

Required reasoning pattern:

intuitional_output(Conclusion, Evidence, Confidence) :-
    candidate_conclusion(Conclusion),
    supporting_indicators(Conclusion, Evidence),
    indicator_reliability(Evidence, Reliability),
    intuition_policy(Policy),
    apply_intuition_policy(Policy, Reliability, Confidence).

Required policies:

* strict: all mandatory indicators present;
* balanced: supporting evidence exceeds contradicting evidence;
* expert_weighted: reliability depends on declared expertise;
* plural: return all sufficiently supported interpretations;
* cautious: return undecided when evidence is weak;
* custom(PredicateName): allowed only for pre-registered safe predicates.

⸻

15. CFG Output Requirements

The system shall produce a declarative CFG independent of Prolog execution details.

Canonical rule:

cfg_rule(
    RuleId,
    LeftHandSide,
    RightHandSide,
    Annotations
).

Example:

cfg_rule(
    r14,
    olfactory_response,
    [floral_stimulus, strong_measurement],
    [
        requires(e17),
        confidence_policy(weighted),
        department(neuroolfaction),
        derived_from([e17, schema_olfactory_v1])
    ]
).

A plain compatibility format such as cfg_rule(LHS, RHS) shall remain exportable.

⸻

16. DCG Output Requirements

Generated DCGs shall support semantic arguments.

Preferred general form:

nonterminal(ParseTree, Semantics, EvidenceState) -->
    ...

Example:

document_interpretation(
    tree(symbolic_reading, Children),
    interpretation(symbolic_reading, Confidence),
    evidence_state(Used, Remaining)
) -->
    symbolic_indicator(Child1, I1),
    contextual_indicator(Child2, I2),
    {
        Children = [Child1, Child2],
        combine_indicator_confidence([I1, I2], Confidence),
        Used = [I1, I2],
        evidence_remaining([I1, I2], Remaining)
    }.

Generated semantic goals shall call only known, exported, approved predicates.

20. Missing and Conflicting Data

Missing values shall be represented explicitly:

missing.
unknown.
not_recorded.
not_applicable.
below_detection_limit.

Conflicts shall not be silently resolved.

Required conflict output:

evidence_conflict(
    ConflictId,
    Subject,
    EvidenceIds,
    ConflictType,
    ResolutionStatus
).

Supported resolution policies:

* retain all;
* prefer newest;
* prefer highest reliability;
* prefer named source;
* average compatible numeric values;
* majority indicator;
* require human review.

21. Confidence and Trust

Confidence shall attach to a proposition or interpretation, not merely to an entire file.

The system shall distinguish:

* Measurement uncertainty;
* Source reliability;
* Observer confidence;
* Interpretation confidence;
* Grammar-rule support;
* Model confidence.

Combining confidence values shall require a declared policy.

The compiler shall not assume that two confidence values are statistically independent.

22. Provenance and Explanation

Required explanation queries:

explain_derivation(+ItemId, +Result, -Explanation).
explain_evidence_use(+EvidenceId, +Result, -Uses).

Example explanation:

Rule r14 was generated because records e17 and e18 classified the
response as strong on the configured ordinal neuroolfactory scale.
The branch is guarded by measurement validity and stimulus-category
checks. Confidence 0.82 came from the weighted-observer policy.

Explanations shall distinguish:

* Direct source statement;
* Computed result;
* Department mapping;
* Heuristic inference;
* Intuitional inference;
* Generated grammar structure.

23. Grammar Optimisation

Existing CFG transformations shall continue to operate, including where applicable:

* Duplicate-rule removal;
* Unreachable-rule removal;
* Unproductive-rule removal;
* Prefix factoring;
* Suffix factoring;
* Unit-production simplification;
* Left-recursion handling;
* Recursion analysis;
* Optional and repetition expansion;
* Rule minimisation.

Optimisation shall preserve evidence annotations.

Two rules with identical syntax but materially different evidence constraints shall not be merged unless their annotations are safely combined.

⸻

24. Safety Requirements

The program shall:

* Use allow-listed predicates in generated semantic actions;
* Parse external terms with restricted syntax;
* Treat all imported strings as data;
* Avoid shell execution;
* Avoid unrestricted module loading;
* Avoid dynamic assertion of unvalidated clauses;
* Prevent path traversal during export;
* Limit file sizes and record counts through options;
* Limit grammar expansion;
* Detect recursive generation without a bound;
* Avoid writing outside the requested export directory;
* Preserve source data without silently modifying it.

Generated code shall contain no calls to unknown predicates.

⸻

25. Performance Requirements

The system shall:

* Stream CSV, TSV, JSON Lines, and large observation tables where practical;
* Avoid loading all source data when only schema discovery is needed;
* Index evidence by identifier, department, type, and subject;
* Cache validated schemas;
* Avoid repeatedly normalising the same evidence;
* Bound grammar-generation depth;
* Detect combinatorial grammar growth;
* Warn before producing excessively large CFGs;
* Support deterministic operation where nondeterminism is unnecessary.

Suggested warning threshold:

max_generated_rules(10000).

The threshold shall be configurable.

37. Coding Standards

* Use SWI-Prolog module declarations.
* Add mode and determinism comments.
* Prefer pure predicates.
* Pass state explicitly where practical.
* Keep parsing, validation, transformation, and export separate.
* Avoid global dynamic state except for controlled registries or caches.
* Use setup_call_cleanup/3 for streams.
* Use library(error) for type checking.
* Use library(option) for options.
* Use library(csv) and library(http/json) where suitable.
* Use plunit.
* Avoid cuts unless their determinism purpose is documented and tested.
* Avoid meta-calls from untrusted data.
* Never suppress diagnostics merely to make tests pass.
